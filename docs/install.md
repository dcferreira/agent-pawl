# Install

For what this build runs, see [status.md](status.md). Each release publishes a Claude Code plugin zip
that bundles the `pawl` binary (see the next section), plus the plain `install.sh` / GitHub Releases
pair for terminal use outside Claude Code. Each release's notes come from `CHANGELOG.md` (generated by
changie from `.changes/`) — see [docs/releasing.md](releasing.md) for how a release is cut.

## Install the plugin (recommended inside Claude Code)

Each release publishes `agent-pawl-plugin_<version>.zip` — the `/agent-pawl:pawl` skill, the
enforcement hooks, and `pawl` binaries for linux/darwin × amd64/arm64 under `libexec/`. The repo's
`.claude-plugin/marketplace.json` lists the plugin with an `archive` source: the latest release's zip,
pinned by its sha256 (Claude Code refuses a zip whose hash doesn't match), and the release job keeps it
current. Add the repo as a marketplace and install the plugin:

```
/plugin marketplace add dcferreira/agent-pawl
/plugin install agent-pawl@agent-pawl
```

The bundled binary is available from v0.6.0 on; v0.5.0 and earlier releases did not publish the
plugin zip, so for those you need a separately installed binary.

Restart the session so the hooks bind. The plugin's `bin/pawl` launcher runs the bundled binary for
your platform; the hooks and the skill use it, so no separate binary install is needed.

**Enable auto-update for the marketplace**: `/plugin` > Marketplaces > agent-pawl > Enable
auto-update, or declare it in `~/.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "agent-pawl": {
      "source": { "source": "github", "repo": "dcferreira/agent-pawl" },
      "autoUpdate": true
    }
  }
}
```

Third-party marketplaces default to auto-update OFF. When on, Claude Code checks after
your first message of a session, with a random delay of up to ten minutes. A new version loads at the
next launch or on `/reload-plugins`; until then the hooks keep using the old plugin path. Because the
binary ships inside the plugin, plugin and binary move together. Without a bundled binary (a source
checkout, or `--plugin-dir`), the plugin's launcher falls back to a `pawl` on `PATH`, and the two can
drift apart. `pawl run` then refuses with exit 4, naming both versions (see
[cli.md](cli.md#pawl-version--human)). A `dev` source build skips that check. Updates are detected by the plugin's `version`: an install
only moves when that changes. To update by hand: `claude plugin marketplace update agent-pawl`, then
`claude plugin update agent-pawl@agent-pawl`.

After a plugin update, a long-lived Claude Code session keeps using the old plugin until you restart
it or run `/reload-plugins`. The old version directory also stays in the plugin cache, marked
`.orphaned_at`; Claude Code's plugin docs say a background cleanup removes it 14 days later (the
marker was observed on Claude Code 2.1.300; the removal was not).

A terminal-installed `pawl` earlier on `PATH` can shadow the plugin's bundled binary (Claude Code appends
the plugin's `bin/` to the end of `PATH`). The `/pawl` skill therefore runs the plugin's own launcher by
path (`"${CLAUDE_SKILL_DIR}/../../bin/pawl"`) rather than a bare `pawl`, and `pawl run` refuses (exit 4)
when its own version differs from that of the plugin whose hooks are active (the hooks' version, recorded
on the PreToolUse heartbeat, wins over the launcher's `PAWL__PLUGIN_VERSION`). This applies to binaries
from this release on: an older shadowing binary has no such check, so keep one `pawl`, or keep both at
the same version.

`pawl update` refuses on a plugin-managed binary (one that lives at
`<plugin root>/libexec/<os>_<arch>/pawl` inside an installed plugin) and tells you to run
`claude plugin update agent-pawl@agent-pawl` instead.

### Migrating from an earlier install

If you already installed the plugin from the `dcferreira/agent-pawl` marketplace and the binary
separately (`install.sh` or `go install`), there is nothing to re-add: update as above. A v0.6.0
install from before the archive source was added came from the repo's old in-tree source, which has
no `libexec/`, and updates are gated on `version`, so it stays on a `PATH` binary until the next
release moves it onto the bundled one. To get the bundled binary now, run `/plugin marketplace update
agent-pawl`, then uninstall and reinstall the plugin (`/plugin uninstall agent-pawl@agent-pawl`, then
`/plugin install agent-pawl@agent-pawl`). Your standalone `pawl` can stay for terminal use or be removed (see
[Uninstall](#uninstall)). (The release-URL form `/plugin marketplace add
https://github.com/.../releases/latest/download/marketplace.json` documented in v0.6.0 does not
work: Claude Code treats any github.com URL as a git repo. If you tried it there is nothing to undo.)

To pin a specific release, download that release's `marketplace.json` asset into
`<dir>/.claude-plugin/marketplace.json` and run `/plugin marketplace add <dir>`; a directory
marketplace stays on that release and does not auto-update. Only the release's own `marketplace.json`
asset pins correctly: a git-ref marketplace (`dcferreira/agent-pawl#vX`) installs the previous release,
because the repo's `marketplace.json` is bumped to vX only after the tag.

Contributors: `claude --plugin-dir .` from a checkout loads the working tree as the plugin; it has no
`libexec/`, so `bin/pawl` falls back to a `pawl` on `PATH` (`go install ./cmd/pawl` / `make install`).
Adding the checkout as a marketplace (`/plugin marketplace add ./`) installs the release zip, not the
working tree, so use `--plugin-dir` to test local plugin changes.

### Using pawl in a terminal outside Claude Code

The bundled binary is not on your shell's `PATH`. For terminal use (`pawl status`, `pawl validate`,
resuming a run), install a standalone copy with `install.sh` or `go install` below. `pawl update` keeps an
`install.sh` copy current; `go install` users re-run `go install ...@latest`. Two copies (the plugin's and the standalone one) are independent and
can drift in version; the run state they share lives under `~/.claude/pawl/`, so keep them
reasonably close.

## Install via install.sh

```
curl -fsSL https://raw.githubusercontent.com/dcferreira/agent-pawl/main/install.sh | sh
```

This detects your OS (linux/darwin) and architecture (amd64/arm64), downloads the matching
`pawl_<version>_<os>_<arch>.tar.gz` and `checksums.txt` from the latest GitHub Release, verifies
the archive's sha256 against `checksums.txt` before extracting anything, and installs `pawl` to
`$HOME/.local/bin` (override with `INSTALL_DIR=...`). It prints a `PATH` reminder if that
directory isn't already on your `PATH`.

Env vars:

- `PAWL_VERSION` — install a specific version (e.g. `v0.1.0` or `0.1.0`) instead of latest.
- `INSTALL_DIR` — install location, default `$HOME/.local/bin`.

It has no dependency on the Go toolchain — only `curl` or `wget`, `tar`, and `sha256sum` or
`shasum` (whichever your OS ships). It fails with an explicit, actionable message on any OS other
than Linux/macOS or any architecture other than amd64/arm64 (e.g. Windows, 32-bit x86), rather
than silently doing the wrong thing.

The pure parts of `install.sh` (OS/arch detection, asset naming, version resolution, checksum-line
parsing) are unit-tested without touching the network in `scripts/test-install.sh` — run via
`make test-install`.

### Upgrading a binary installed this way

Once you have a standalone release binary installed (via `install.sh` above, or otherwise), `pawl update`
upgrades it in place — same checksum verification as `install.sh`, no need to re-run the curl
one-liner:

```
pawl update
```

`pawl update` refuses on the plugin's bundled binary — update that with `claude plugin update agent-pawl@agent-pawl` (or marketplace auto-update). See [cli.md](cli.md) for `--check`, `--version` (pin/rollback) and `--force`. A
binary built from source (`pawl version` prints `pawl dev`) is a different case — see the note
right below.

## Build and install the binary

You need Go (this build was developed and tested against Go 1.27) and a clone of this repo.

```
make install
```

This is exactly `go install ./cmd/pawl` (see the `Makefile`). It builds `cmd/pawl` and drops `pawl` at
`$(go env GOPATH)/bin/pawl` — make sure that directory is on your `PATH`. Equivalently, if you don't
want to clone the repo yourself, install straight from the published module:

```
go install github.com/dcferreira/agent-pawl/cmd/pawl@latest
```

`@latest` resolves to the latest tagged release (pin one with `@vX.Y.Z` instead), but it's still a
source build, so `pawl version` still prints `pawl dev` rather than the tag — use `install.sh` if
you want a stamped release binary.

If you'd rather not touch `$GOPATH/bin`, `make build` puts the binary at `./dist/pawl` in the repo
instead (not `./bin/`, which is a committed plugin directory — see the plugin section below):

```
make build
./dist/pawl version
```

## Verify

```
pawl version
```

prints `pawl dev` for anything built from source with plain `go build`/`go install`/`make
install`/`make build`, because those don't set the `-ldflags "-X main.Version=..."` that
`cmd/pawl/main.go` supports — `pawl dev` is what building from source correctly looks like, not a
symptom of a bad build. A binary installed via `install.sh` prints the released version instead
(e.g. `pawl 0.1.0`, no leading `v` — `.goreleaser.yaml` sets that ldflag to goreleaser's
`{{.Version}}` template value, which is the tag with its `v` stripped, not the raw git tag).

A `pawl dev` (source) build is exactly what `pawl update` refuses to touch without `--force` — see
[cli.md](cli.md) — since overwriting a build you made yourself with a
downloaded release binary is not something `pawl update` should ever do by default.

```
pawl
```

with no arguments prints the command list — `run`, `validate`, `status`, `abandon`, `list`,
`submit`, `poll`, `hook`, `version`, `update`. That is the complete command surface of this build. In particular:

- **`pawl hook pre|stop|subagent-stop`** is the enforcement hooks' entry point — see [#hooks](#hooks) below.
- **`pawl run` refuses to start (exit 4) without a live `PreToolUse` heartbeat**, unless you pass
  `--no-enforcement` or set `PAWL_ENFORCEMENT=off` — see [#hooks](#hooks) and
  [dogfood.md](dogfood.md) for what that means in practice.

## Hooks

`pawl run` won't start unless `pawl`'s `PreToolUse` hook has fired for this working copy within the last
5 minutes — its way of confirming the enforcement hooks are actually wired up, since it has no
other way to ask Claude Code that directly. Without a fresh heartbeat, `pawl run` refuses:

<!-- pawl-capture: cli/refuse-no-heartbeat -->
```
$ pawl run hello name=ada
pawl: refusing to start: pawl's PreToolUse hook has not fired for this working copy in the last 5 minutes.
Install the agent-pawl Claude Code plugin (docs/install.md#hooks), or pass --no-enforcement.
Diagnosis:
  - CLAUDE_CODE_SESSION_ID is not set, so the session-keyed heartbeat (written by pawl >= 0.4.0) cannot be looked up; only this working copy's heartbeat was checked.
  - no heartbeat for working copy /home/you/project
exit 4
```

Allowlisting `Bash(pawl:*)` in Claude Code's permissions avoids an approval prompt on every `pawl`
call — worth doing on its own, and it also means the heartbeat gets written without you having to
wait on a prompt first.

The heartbeat is written twice: per working copy (the hook payload's `cwd`, which in Claude Code is
always the session's start directory) and per session (`~/.claude/pawl/heartbeat/session/<id>.json`).
`pawl run`/`submit`/`poll` use the session one when Claude Code's `CLAUDE_CODE_SESSION_ID` is exported
to the Bash call — so a session may `cd` into another working copy and still start enforced runs there —
and fall back to the working-copy one otherwise.

**The Claude Code plugin wires the hooks automatically.** Once installed (see the README's
Install section), the plugin's `hooks/hooks.json` binds `PreToolUse` (matcher `Bash`), `Stop` and
`SubagentStop` to `${CLAUDE_PLUGIN_ROOT}/bin/pawl-hook pre|stop|subagent-stop` — a fast-path wrapper that
hands the payload to `pawl hook pre|stop|subagent-stop` once anything is actually live, or (for `pre`/`stop`
only) once the payload itself mentions `pawl` (so a fresh heartbeat is written even before any run is
live). Nothing further to configure; restart the
session after installing so the hooks bind.

**Without the plugin**, add the same three hooks to your own `settings.json` directly — there is no
`pawl-hook` on your `PATH` to fast-path through, so these call `pawl hook pre`/`pawl hook stop`/
`pawl hook subagent-stop` straight:

```json
{
  "hooks": {
    "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "pawl hook pre" }] }],
    "Stop": [{ "hooks": [{ "type": "command", "command": "pawl hook stop" }] }],
    "SubagentStop": [{ "hooks": [{ "type": "command", "command": "pawl hook subagent-stop" }] }]
  }
}
```

**Recommended: wrap each call so it fails open.** Claude Code reads a hook's exit code 2 as "block".
A `pawl` binary older than the hook subcommand you wire exits 2 for an unknown command. Unwrapped, that exit 2 would deny every Bash call
(including the reinstall that fixes it) and refuse every end of turn. The plugin's `bin/pawl-hook`
maps every non-zero exit to exit 1, which Claude Code treats as a non-blocking error. Do the same:

```json
{
  "hooks": {
    "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "sh -c 'pawl hook pre; s=$?; [ $s -eq 0 ] || exit 1'" }] }],
    "Stop": [{ "hooks": [{ "type": "command", "command": "sh -c 'pawl hook stop; s=$?; [ $s -eq 0 ] || exit 1'" }] }],
    "SubagentStop": [{ "hooks": [{ "type": "command", "command": "sh -c 'pawl hook subagent-stop; s=$?; [ $s -eq 0 ] || exit 1'" }] }]
  }
}
```

The payload on stdin still reaches `pawl`, and on exit 0 its stdout, including a JSON deny/block
decision, passes through unchanged. A real `pawl hook` never exits 2 itself: it allows with exit 0
and no output, and denies or blocks with exit 0 and a JSON decision on stdout.

Without the `SubagentStop` entry the `Stop` hook still works, but you keep a race: a background subagent
that finishes just before the turn ends is already gone from the Stop payload's `background_tasks` while
its completion notification is still queued, so `Stop` refuses a turn Claude Code was about to wake
anyway. `subagent-stop` records a short-lived (60s), single-use marker that lets that one Stop through.

**Opting out**: pass `--no-enforcement` to `pawl run`, or set `PAWL_ENFORCEMENT=off` — the banner
says so (`enforcement: off (--no-enforcement)` / `enforcement: off (PAWL_ENFORCEMENT=off)`), and any
`guards:` the workflow declares are reported as declared but not enforced. This is a real, visible
opt-out, not a workaround: nothing is checked for that run. The opt-out is recorded in the run's
journal at start and holds for the run's whole life — the hooks ignore it (no guards, no subagent VCS
rule, no `Stop` refusal) even on resume, submit or poll. It works the other way too: an opted-out
run resumes without a heartbeat, and an enforced run can't be opted out on resume (`pawl run`
refuses `--no-enforcement` there). An enforced run doesn't need a heartbeat to resume either: you can
resume it from a plain terminal, and it stays enforced. See [cli.md](cli.md).

Once hooks are on, `Stop` will refuse to end the driving session's turn while its run is at an
`agentic`/`parallel` step awaiting `pawl submit` — finish the dispatch, or run
`pawl abandon --run <id>` to release it. See [cli.md](cli.md) and
[troubleshooting.md](troubleshooting.md) for the exact messages.

## What `make check` runs

```
make check
```

runs `go fmt ./...`, `go vet ./...`, `go test ./...`, `scripts/test-install.sh` (install.sh's
unit tests), and `scripts/release/test-checks.sh` (the release check scripts' unit tests). This is
the same check a change to this repo is expected to pass; running it after
`make install` is a reasonable sanity check that your Go toolchain and checkout are in order,
though it is not required just to use the binary.

## Uninstall

```
rm $(go env GOPATH)/bin/pawl
```

or, if installed via `install.sh`:

```
rm "${INSTALL_DIR:-$HOME/.local/bin}/pawl"
```

To remove the plugin instead, use `/plugin` (or `claude plugin uninstall agent-pawl@agent-pawl`), which removes its bundled binary too.

There is no other installed state from the binary install itself to remove: no plugin directory, no
global `~/.local/state/pawl/`. `~/.claude/pawl/` does now hold state — `runs/`, `live/`, and
`heartbeat/`, written by the enforcement hooks — but that's plugin/hook state, not something this
binary uninstall touches; remove it by hand if you also want that gone. Where run state actually
lives is `internal/journal`'s run directory — see `docs/running.md` and `pawl status`'s `root:` line
for the mechanism that exists today.
